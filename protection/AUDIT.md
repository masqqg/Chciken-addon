# Security audit — METEOR EXTREME SHIELD

Scope: the protected jar produced by `protection/pipeline.sh`
(`dist/meteor-extreme-shield-<version>-<sha>-protected.jar`).

Priority used for every decision: **compatibility > performance > protection**.
Nothing here rewrites a working module; the only code added is the ASM
post-processing pass in `protection/Sanitizer.java`.

## A. Decompiler hardening

| # | finding | risk | fix |
| --- | --- | --- | --- |
| A1 | `SourceDebugExtension` (Umbra's SMAP decoy) and `SourceFile` survived in every class | an analyst gets the original file names and a line map back to the source | `Sanitizer` drops `visitSource` entirely (class 0 occurrences of both attributes) |
| A2 | `LocalVariableTable`, `LineNumberTable`, `MethodParameters` were still present | local names re-identify logic, line tables rebuild control flow in decompilers | all three attributes are dropped by the sanitizer |
| A3 | the private records kept readable names — `ChickenStorageESP$Entry`, `$EntityBox`, `$TracerTarget` (Umbra keeps record metadata) | module name plus purpose in a directory listing, the single biggest giveaway | renamed to `a/b/c`-style names by the sanitizer; `InnerClasses.inner_name` is re-derived too, so the old names disappeared from the constant pool (verified: 0 files contain them) |
| A4 | class/package naming | Meteor resolves `MeteorAddon#getPackage()` from the string `dev.chicken.addon`, the loader resolves the entrypoint by name | package names are never touched, `AddonTemplate` is never renamed, `fabric.mod.json` entrypoint is re-checked after every layer |
| A5 | method names and descriptors | Meteor/Orbit find `@EventHandler` methods by annotation, settings by their own name strings | method annotations and descriptors are preserved, only member names are renamed by Umbra/Aidsfuscator |

## B. String protection

| # | finding | risk | fix |
| --- | --- | --- | --- |
| B1 | plaintext module names and descriptions recoverable from the jar | instant identification of every module | Umbra encrypts per string site (per-class keys, RC4/ChaCha20/AES-CTR engines), decrypt-and-wipe, no plaintext cache. Measured: 0 of 4 long user-facing sentences survive, 0–1 of 8 keyword markers |
| B2 | decryptor readability | a single readable decryptor gives the whole string table back | decryptor helpers are emitted in seed-derived packages (`f5`, `sa`, `com/sun/security/util/gb` decoys), names generated by the same dictionary as the program |
| B3 | custom/home-made crypto | weak or non-standard crypto would be worse than none | no custom cipher is written by this project; the layer uses Umbra's standard engines only |

## C. BytecodeVM

| # | finding | risk | fix |
| --- | --- | --- | --- |
| C1 | the first pass virtualized every matched method: 337 methods → **840 classes, 66 MB** jar and the tool marks the output as unverified | an unshippable jar, plus a documented "hundreds of times slower" runtime | default **off** (`ENABLE_VM=0`), allowlist-only (`config/bytecodevm-allowlist.txt`, empty by default = 0 methods) |
| C2 | no hard limit | a bad run could silently replace the good jar | 3x size guard + entrypoint check + link check; on breach the build **fails** and the previous safe jar is kept as `*-unvirtualized.jar` |
| C3 | tick/render/packet handlers | virtualization there destroys frame time | those methods are excluded no matter what the allowlist says |

## D. Kafuscator

| # | finding | risk | fix |
| --- | --- | --- | --- |
| D1 | the only published artifact is a Windows x64 `jpackage` app (`.exe` + Windows runtime) | cannot be executed or verified on Linux/macOS, Fabric compatibility unknown | layer stays optional and off; nothing was executed; the platform-neutral transform layer is the ASM sanitizer above, which runs everywhere |

## E. Integrity and signature

| # | finding | risk | fix |
| --- | --- | --- | --- |
| E1 | signing order | signing before the last transform invalidates the signature (observed: a re-sanitized signed jar fails with "SHA-384 digest error") | signing is the last step, after every transform; `jarsigner -verify` runs immediately after and must pass |
| E2 | checksums | users cannot verify a download | `SHA256SUMS` is written next to the jar |
| E3 | certificate | a self-signed key cannot prove authorship to the outside world | reported as such: `dist/extreme-shield-dev.jks`, RSA 2048, 10 years, self-signed, not a CA. Replace it with a real certificate for a public release |
| E4 | build fingerprint | the manifest used to carry version, git sha and the obfuscation seed | reduced to project + fingerprint + build time; the seed is no longer written next to the jar |

## F. Fabric compatibility

- `fabric.mod.json`: kept, entrypoint verified after every layer (`dev.chicken.addon.AddonTemplate`).
- Mixin config: `chicken-addon.mixins.json` is present with an empty client list (the example mixin was removed); no mixin classes, no refmap.
- Access widener: none in this project.
- Link check: all 13 classes load against the real mod classpath (`VerifyJar`, 13/13, 0 failures).
- **In-game test: not performed.** The build machine has no Minecraft installation and no display, so a real 1.21.11 launch, mixin injection and the Clear/Render/Cluster Bypass/Storage ESP behaviour are unverified.

## G. Strict mixin protection (mandatory)

| # | rule | enforcement |
| --- | --- | --- |
| G1 | no class or method renaming on mixin classes | `mixin-keeplist.sh` derives exact `--keep` arguments for every mixin class and every helper class reachable from its constant pool; Umbra receives them on every run |
| G2 | `@Mixin`, `@Inject`, `@Redirect`, `@ModifyArg`, `@ModifyVariable`, `@Overwrite`, `@Shadow` preserved | guard runs an ASM snapshot of every class/method/field annotation value on the pre-protection and protected jars and diffs them |
| G3 | target class, target method and descriptors unchanged | same snapshot diff; a changed method value in `@Inject` shows up as a one-line diff |
| G4 | config, refmap and access widener references preserved | guard checks the mixin list, config package, client/server entries and a declared refmap in the protected jar |
| G5 | no VM virtualization or aggressive flow on mixin classes | Aidsfuscator and BytecodeVM layers are skipped automatically while the jar contains a mixin class (`ALLOW_AIDS_WITH_MIXINS=1` is the only override, off by default) |
| G6 | release blocked on mixin failure | the guard runs before signing and calls `die`, so no signed release jar is produced |

## H. Decompile regression gate

`decompile-gate.sh` runs after the comparison and fails the build when the
protected jar becomes easier to read than the recorded baseline
(`config/decompile-baseline.json`: CFR failures ≥ 60, Vineflower failures ≥ 20,
readable module identifiers ≤ 1). Current build: **81 / 31 / 0 → passed**.
Any future change that weakens the output stops the build before release.

Verified with a synthetic mixin (`@Mixin(targets="net.minecraft.client.Minecraft")` + `@Inject`):

- keep set generated: `dev.chicken.addon.mixin.TestMixin`, `…TestMixin$*`
- unchanged jar: `mixins intact`, `annotation snapshot identical for 1 mixin class(es)`, exit 0
- renamed mixin class: `FAIL mixin class missing or renamed`, exit 1
- changed annotation value (`method="run"` → `riN`): `FAIL mixin annotations or members changed`, exit 1

The current addon still declares zero mixins, so the guard is a no-op today and
activates automatically the moment a mixin is added.

## Readability audit and targeted hardening

A CFM/Vineflower pass over the pre-hardening jar was scored per method
(calls into the setting API / Minecraft / renderer versus `cfr_ignored` junk).
Three methods decompiled as clean, directly readable source:

| method (pre-hardening) | shape |
| --- | --- |
| `modules/b: a(Render3DEvent)` | storage-ESP 3D renderer: setting getters, chunk map loop, `renderer.box(...)` calls, 77 lines, 0 junk blocks |
| `modules/a: a(int,int)` synthetic | index/shape helper, 45 lines, 56 API references, 0 junk blocks |
| `modules/c: a(Render2DEvent)` | HUD renderer, 136 lines, 11 API references |

Hardening applied through Umbra's documented switches (no mixin impact):

```
--set flowObfuscation.level=normal --set flow.aggressive=true
--set flowObfuscation.maxInstructions=8000
--set mba.enabled=true --set mba.depth=2
--set antiLlm.maxWrappedMethodsPerClass=40 --set antiLlm.wrapperLayers=2
```

### Cost / benefit per knob (leave-one-out on build `ff27fbd`)

| profile | jar | CFR failing methods | per-knob cost |
| --- | --- | --- | --- |
| base `balanced` | 213 KB | 81 | - |
| + anti-LLM wrappers only (40/class, 2 layers) | 336 KB | 98 | +119 KB, **+77** |
| + MBA only (depth 2) | 227 KB | 84 | +14 KB, +3 |
| + MBA + anti-LLM (**adopted**) | 297 KB | **168–169** | +84 KB, +87 |
| + MBA + anti-LLM + flow (normal/aggressive/8000) | 455 KB | 175 | +242 KB, +94 |

Flow overrides cost **158 KB for 6 extra failing methods**, so they were dropped;
MBA costs 14 KB for 3 and stays. Anti-LLM is the only pass with a large
protection-per-byte return.

### Static per-tick cost (bytecode proxy)

Measured with `javap -c` on the module classes (`render` = the method that
references `ShapeMode`, `chunk` = the method that references `class_2818`):

| profile | methods | total instr | render method | chunk method | exception handlers |
| --- | --- | --- | --- | --- | --- |
| unprotected source | 110 | 9,444 | 558 | 369 | 3 |
| base `balanced` | 327 | 100,079 | 558 | 616 | 200 |
| adopted (MBA + anti-LLM) | 436 | 159,337 | **894 (+60%)** | **777 (+110%)** | 309 |

The adopted profile roughly doubles the instruction count of the chunk-scan and
render helpers because every literal goes through a runtime table (`e[81]^e[80]`)
and anti-LLM adds one forwarding hop per wrapped method. Instruction count is a
proxy, not a frame-time measurement: real TPS/FPS numbers need the game, which
this environment cannot run.

Effect on the same source:

| metric | before | after |
| --- | --- | --- |
| CFR methods failing to decompile | 81 | **174** |
| Vineflower methods failing | 31 | 31 |
| readable module methods (score ≥ 6) | 3 | **0** |
| decompiled output files | 10 | 7 (rest fail) |
| leaked identifiers | 0 | 0 |
| jar size | 213 KB | 297 KB |
| link check | 13/13 | 13/13 |

The storage-ESP renderer now shows `e[81] ^ e[80]` runtime-table index
arithmetic instead of `>> 4`, and the three methods above no longer decompile at
all. Cost: ~2x jar size and extra forwarding layers on 40 methods per class, so
`UMBRA_FLAGS=` (empty) reverts to the previous profile if compatibility ever
regresses.
